# CLAUDE.md — bard.realm.watch

Guidance for Claude Code working in this repository.

## What this is

The standalone Bard **device** project and its public face: a ~260,000-parameter
TinyStories-class transformer (int8, executed in place from flash) generating endless
stories on a microcontroller. Shipped inside [smol](https://github.com/jphein/smol) as
`--features bard` ([smol#300](https://github.com/jphein/smol/issues/300)); given its own
project and its own chip under
[smol#347](https://github.com/jphein/smol/issues/347).

**This repo contains the project, the docs, and the Pages site. It does not contain
firmware, and it is not going to.** That is the design, not a gap waiting to be filled.

The Bard's source stays in smol. `bard` was dropped from smol's `REPRO_FLEET_FEATURES`
(smol `a5b1312`) because on the ESP32-C3 the model's DRAM comes straight out of the
runtime stack and starves the radio; the **feature itself stays**, and smol's
`tools/gate.sh` builds a `bard` tier (smol `1efb8b5`) so it cannot rot. On an ESP32-S3 —
the next fleet target — and on the C6, there is DRAM for both, and the Bard is just a
smol feature switched on. The "Bard device" is a smol build with the right features on a
chip with the right memory.

## Repository shape

```
index.html            the Pages site — single file, no build step, no external requests
favicon.svg           theme-aware, inline @media (prefers-color-scheme)
version.json          realm-sigil payload            ─┐ both generated by
api/version           the same document, standard path ┘ tools/stamp.sh
stories/stories.json  stories the model produced, newest first
tools/stamp.sh        realm-sigil stamp wrapper
CNAME                 bard.realm.watch
```

GitHub Pages serves the **`main` branch at root** — a push to `main` is a deploy. There
is no workflow and no staging branch; keep it that way unless a build step becomes
genuinely necessary.

## Rules that are load-bearing here

1. **Never copy the firmware in — not now, not after `smol-core` lands.** This is the
   rule most likely to be broken by someone being helpful: the repo is named after the
   Bard, so importing `nano_llm.rs` looks like tidying up. It is not. It would create a
   second copy of the model runtime and a *third* hand-copied `names.rs`/`sigil.rs` (the
   esp32c6-watch is already the second), which is the divergence smol#347 exists to
   eliminate. If a change belongs to the Bard's code, it belongs in smol behind
   `--features bard`.

2. **Never fabricate a story.** `stories/stories.json` holds text the model actually
   produced. Every entry carries `origin` (`device` or `reference`), the firmware
   version, and a `provenance` string that says how the text is known to be genuine. A
   plausible-looking sentence written by an assistant would destroy the only thing this
   page is for. If there is no story, the page's empty state is the correct output.

3. **This repo is public.** No LAN addresses, no MAC addresses, no internal hostnames,
   no broker credentials. MQTT topics are fine; the endpoints they live on are not.

4. **Both themes, always.** Light and dark via `prefers-color-scheme` over CSS custom
   properties, with `:root[data-theme=…]` overriding in *both* directions so the manual
   toggle wins regardless of system setting. Adding a colour means adding it to all
   three blocks.

5. **No external requests.** No CDN scripts, no web fonts, no remote images. The page
   must render fully offline; the favicon and the texture are drawn, not fetched.

## Versioning

House convention — [realm-sigil](https://github.com/jphein/realm-sigil), realm
`fantasy`. Run `./tools/stamp.sh` before any commit that changes `index.html`, and
commit the regenerated `version.json` + `api/version` alongside it, or the site
advertises a stale hash.

Registered in `status.realm.watch/checks.json` under `http` (reachability) and
`version` (`https://bard.realm.watch/api/version`).

## Numbers worth not re-deriving

From smol#300 / #302, measured on hardware:

| | |
|---|---|
| parameters | ~260,000, int8, XIP from flash |
| `.rodata` cost | +287,392 B (~281 KB) |
| `.bss` + `.data` cost | +39,072 B — comes straight out of the runtime stack |
| heap / working set | ~96 KB (`Bufs` = 98,180 B; KV caches dominate) |
| `SEQ_CAP` | 80 tokens, sliding window |
| throughput | 202 ms/token bounded, 224–274 ms/token endless |
| stack high-water | 55,440 B, byte-identical across 5 consecutive reports |

The `.stack` figure is the reason this project exists: on the C3 the linker gives
`.stack` whatever DRAM survives `.bss` and shrinks it **silently**, so a successful link
is not evidence of a runnable image. Any claim about fit must come from a measured stack
region, never from "it built".

## Story pipeline (not built)

Planned path, deliberately reusing what the fleet already does:

```
node → MQTT smol/<node>/bard/story → collector → stories/stories.json → Pages
```

Two upstream constraints the collector must respect:

- **~490 B per publish.** The gateway's MQTT buffer caps a publish near 490 bytes, so a
  story arrives as numbered fragments and is reassembled — never assume whole payloads.
- **Retained topics persist after their publisher is gone.** Treat a *flip to a new
  value* as liveness. Presence of a retained payload proves nothing.
